# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Portus is a lightweight desktop GUI for Docker: a Tauri 2 app with a Rust backend (talks to the Docker daemon via `bollard`) and a React 18 + TypeScript + Tailwind frontend (Vite). There are no tests or linter configured yet.

## Commands

```bash
npm install
npm run tauri dev      # run the full desktop app (starts Vite on :1420 via beforeDevCommand)
npm run tauri build    # production bundle (runs `npm run build` first)
npm run build          # frontend only: `tsc -b && vite build` (also the way to type-check)
cargo check --manifest-path src-tauri/Cargo.toml   # type-check the Rust backend
```

`npm run dev` alone serves only the frontend in a browser; every backend call will then fail (see below). A running Docker daemon is required for anything useful.

## Architecture

**Request flow:** React page → `src/lib/api.ts` → Tauri `invoke` → `#[tauri::command]` in `src-tauri/src/commands.rs` → `src-tauri/src/docker/*.rs` → `bollard`. Each command calls `docker::connect()` (local defaults) per invocation; there is no shared client state.

**Adding a backend capability touches four places that must stay in sync:**
1. `src-tauri/src/docker/<area>.rs` — the Docker logic.
2. `src-tauri/src/commands.rs` — the `#[tauri::command]` wrapper (errors are `Result<_, String>`).
3. `src-tauri/src/main.rs` — register it in `tauri::generate_handler![...]`.
4. `src/lib/api.ts` + `src/lib/types.ts` — the typed wrapper and TS mirror of the Rust struct.

Rust structs crossing the boundary use `#[serde(rename_all = "camelCase")]`, so `types.ts` fields are camelCase versions of the Rust fields. Command argument names, by contrast, are passed as-is in the `invoke` args object (Tauri converts snake_case params to camelCase on the JS side).

**Docker engine management (`src-tauri/src/docker/engine.rs`):** Portus does not require Docker Desktop. `docker::connect()` delegates to `engine::connect()`, which uses whichever endpoint `engine::detect()` last found answering: the local socket/named pipe first, then the WSL engine at `tcp://127.0.0.1:2376` over **mutual TLS** (there is no plaintext TCP endpoint). `get_daemon_info` re-runs `detect()` on every poll and reports `managed` (true for the WSL engine). When nothing answers, the frontend (`AppShell` -> `EngineSetup`) calls `get_engine_status` and drives a small state machine (`ready | stopped | notInstalled | restartRequired | wslUnavailable | unsupported | error`, always returned as data, never as `Err`, so the UI always has a message): `stopped` auto-starts, `notInstalled` offers `install_engine`, and `restartRequired` (a dockerd that Portus did not start, e.g. systemd's or `service docker start`, is already running in the distro without the TLS endpoint) offers `takeover_engine` after a confirmation. `running_kind()` tells the cases apart by looking for `/etc/portus/tls` in the running dockerd's command line; `takeover` runs `TAKEOVER_SCRIPT` (stop and disable docker.service/docker.socket, stop dockerd, remove a stale pid file) and then the normal start, so images and volumes are kept but running containers are stopped. `status()` tries the distro saved in `settings.json` first. Installing pipes `INSTALL_SCRIPT` (Docker's official apt repo, Ubuntu/Debian only) into `sh -s` in the distro. Starting first runs `PREPARE_SCRIPT` in the distro (private CA + server/client certs under `/etc/portus/tls`, and the `/usr/local/bin/portus-dockerd` wrapper), copies the client certs to `%LOCALAPPDATA%\Portus\tls\{ca,cert,key}.pem` (the standard Docker file names, so `DOCKER_HOST=tcp://127.0.0.1:2376 DOCKER_TLS_VERIFY=1 DOCKER_CERT_PATH=...` works for the CLI), then launches the wrapper through `cmd /c start` in its own hidden `wsl.exe` session. That session is deliberately **not** a child of Portus, so the engine and its containers survive Portus closing, crashing, or being killed with its process tree (it also keeps the distro alive). Do not quote the distro name in that `start` command line: `wsl.exe` then silently does nothing. Users can opt into stopping the engine on exit (`settings.json` in `%LOCALAPPDATA%\Portus`, `stopEngineOnExit`, default false; handled by `RunEvent::Exit` -> `EngineManager::shutdown`) or stop it with the Dashboard's "Stop Docker" (`stop_engine`, after which `EngineSetup` must not auto-restart it: see `src/lib/engineFlags.ts`). Progress is streamed as `engine-log` events; only `error` statuses carry a log. Event listening needs the capability in `src-tauri/capabilities/default.json` (`core:default`).

**Errors from actions are surfaced globally:** `main.tsx` installs a `MutationCache.onError` that shows a toast (`src/lib/toast.ts`, `Toaster`) for any failed mutation. Give each `useMutation` a `meta: { label: "..." }` so the toast says what failed. Tauri rejects `invoke` with the plain `Err(String)`, so use `errorMessage()` from `src/lib/utils.ts` rather than `error.message`.

**No mock data.** `api.ts` throws if `__TAURI_INTERNALS__` is absent (i.e. running in a plain browser). Pages surface this via `ConnectionError`. `get_daemon_info` deliberately returns `connected: false` instead of an error when Docker is unreachable, so the dashboard can render a disconnected state.

**Logs use two mechanisms:** `list_recent_logs` is polled by `Logs.tsx` (react-query `refetchInterval`) and returns the last lines of up to 5 running containers; `stream_container_logs` spawns a background task that pushes `container-log` / `container-log-error` events to the frontend via `app.emit`. Log level is guessed from message text in `docker/logs.rs`.

**Tables and detail pages:** every list table sorts by column through `useSort` (`src/lib/sort.ts`) and `SortableTh`: a click cycles descending, ascending, then back to the default order, which puts running containers / images and volumes in use on top (the default order is also the tie-breaker). Rows link to detail pages (`/containers/:id`, `/compose/:name`, `/images/:id`, `/volumes/:name`), which cross-link each other (a container links to its image, compose project and volumes; images and volumes list the containers using them). Ids and names go through `encodeURIComponent` in the URL. `ContainerSummary.volumes`, `ImageSummary.repoTags` and `ComposeService.containerId` exist for those links.

**Dashboard metrics:** `get_daemon_info` also returns `cpus`, `memTotalMb`, and the containers' summed `cpuPercent` (already divided by `cpus`) and `memUsedMb`. `AppShell` records each poll into the in-memory `useMetrics` store (`src/lib/metrics.ts`, last 10 minutes), so history accrues whichever page is open; the Dashboard draws it with `UsageChart` (plain SVG with theme tokens, crosshair tooltip, arrow-key navigation).

**Frontend:** `HashRouter` + routes in `src/App.tsx` inside `AppShell`; server state via `@tanstack/react-query` (query keys like `["containers"]`, `["logs"]`); the zustand stores are the appearance one (`src/themes/store.ts`) and the toast one (`src/lib/toast.ts`). Shared primitives live in `src/components/ui/`. Use the `@/` alias for `src/` imports.

**Theming (`src/themes/`) is the single place that defines how the app looks.** A theme is plain data (`Theme` in `types.ts`) covering: colors (any of them may carry alpha, `#RRGGBBAA`, for glass looks), corner radii per role, shadows (`card`, `overlay`, plus `control` = a raised button and `inset` = a pressed button or text field, which is how bevel/neumorphic looks work), border width and style, a spacing `density` multiplier, the keyboard focus outline, effects (`surfaceBackdrop` blur for frosted glass, `canvasImage` for gradient backgrounds) and fonts. The sidebar has its own colors (`sidebar*`). The vocabulary lives once in `tokens.ts`; from it `css.ts` builds the CSS variables applied on `<html>` at runtime (`applyTheme`), `tailwind.ts` generates Tailwind's `theme.extend` (imported by `tailwind.config.ts`; its spacing scale is multiplied by `--density`), and `ThemePicker`/`ThemePreview` render the UI. **To add a theme, drop a file in `src/themes/definitions/` that default-exports `defineTheme({...})`, or an array of them for a light/dark family** (see `light.ts`, `neo-brutalism.ts`); `registry.ts` discovers it with `import.meta.glob`, validates the colors at startup and requires unique ids, so no other file changes. Only the 11 required colors are mandatory: `defineTheme` derives `accentHover`, a readable `accentForeground`, and the whole sidebar set from them (the active nav label is nudged to 4.5:1 contrast), and fills shape/effects/fonts from defaults. Adding a *token* means adding it to `tokens.ts` and giving it a default in `define.ts`. The store (`persist` under `portus-appearance`) supports a fixed theme or "match system" with separate light and dark picks, and migrates the old `portus-theme` key. When adding or editing themes, check contrast (WCAG): text vs surface and canvas, muted text at 3:1, status colors on `surfaceHover` (status pills), accent vs its foreground.

Style rules so every theme works: never hard-code colors, `rounded-lg/xl/2xl/full`, `shadow-*` sizes, `text-white`, `focus:ring-*` or pixel spacing. Use the semantic classes generated from the tokens: colors (`bg-surface`, `text-text-secondary`, `bg-accent text-accent-foreground`, `text-danger`, `bg-sidebar`/`text-sidebar-text`, ...; opacity modifiers such as `bg-accent/10` multiply the theme's own alpha), radii by role (`rounded-control` for buttons/inputs, `rounded-tile` for icon tiles and toasts, `rounded-card` for panels, `rounded-pill` for badges and bars; a plain status dot may stay `rounded-full`), shadows by role (`shadow-card`, `shadow-overlay`, `shadow-control active:shadow-inset` on buttons, `shadow-inset` on inputs; do not put a shadow on tiny elements such as a switch knob: a theme may make it a large hard offset), and `border`/`divide-*` (width and style come from the theme). Keyboard focus is styled globally (`:focus-visible` in `index.css`), so do not add focus classes or `outline-none`. Glass themes make every `bg-surface` element a backdrop-filter stacking context, so: floating panels (popovers, toasts) must use `bg-surface-solid` (surface over an opaque canvas) instead of `bg-surface`, anything that must overlap the page needs an explicit `z-*` on its positioned ancestor (the header is `z-30`), and an absolutely positioned icon placed before a `bg-surface` input needs `z-10`. Sizes use Tailwind's spacing scale so they follow density; avoid fixed `px` offsets (e.g. a switch knob moves with `translate-x-full`). `dark:` variants follow the active theme's `scheme`.
